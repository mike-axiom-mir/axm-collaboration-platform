======================================================================
1. WHY THESE TWO MODULES EXIST
======================================================================

AXM already has a large machine-readable capability inventory, approximately
1,200 platform capabilities and approximately 1,800 local capabilities at the
time of discussion.

Machine manifests and capability declarations can preserve what the system can
do, but they do not automatically explain those capabilities to humans.

Without a human translation layer, capability growth becomes difficult to:

- discover;
- understand;
- teach;
- connect to practical interfaces;
- expose safely to beginners;
- compare by cost and difficulty;
- combine into human or AI learning paths;
- verify as genuinely usable rather than merely declared.

The paired system solves two different but connected questions.

MODULE A:
"What is this capability, what does it mean, why does it matter, and how can a
human or AI learn to use it?"

MODULE B:
"Which human interface should expose this capability for this user, task,
device, environment, and skill level, and why is that interface the lowest-cost
honest fit?"

The modules must remain separate. They cooperate through one versioned shared
contract.

SOURCE-OF-TRUTH RULE:

The original machine capability declaration remains the technical source of
truth.

The Human Capability Atlas may translate, explain, classify, and organize it.

The Human Interface Intelligence module may recommend ways to expose it.

Neither module may silently modify, expand, or claim a technical capability
that is absent from the source declaration.

3. MODULE A — AXM HUMAN CAPABILITY ATLAS
======================================================================

WORKING NAME:
AXM Human Capability Atlas

PURPOSE:
Translate machine capability declarations into human-readable, teachable,
searchable, interface-ready knowledge without replacing the original machine
registry.

PRIMARY QUESTIONS:

- What is this capability?
- What does it actually do?
- Why might a person use it?
- What problem does it solve?
- Which inputs does it require?
- Which outputs does it produce?
- What can a human do with it?
- What can an AI do with it?
- How can a human and AI collaborate through it?
- What does it cost in compute, time, attention, setup, and skill?
- What are its risks, limitations, dependencies, and failure modes?
- What proof exists that it works?
- How can it be learned?
- Which interfaces can realistically expose it?

----------------------------------------------------------------------
3.1 CAPABILITY CARD
----------------------------------------------------------------------

Every capability should receive a Capability Card linked to its original,
stable capability identifier.

Minimum fields:

1. Capability ID
   Permanent link to the original machine declaration.

2. Capability revision
   Source revision or explicit UNKNOWN.

3. Human name
   Understandable without requiring specialist terminology.

4. Plain explanation
   What the capability actually does.

5. Why it matters
   What problem or human goal it serves.

6. Simple examples
   Concrete uses recognizable by a beginner.

7. Required inputs
   What information, files, devices, permissions, or resources are needed.

8. Optional inputs
   Inputs that improve or alter the result but are not mandatory.

9. Outputs
   What the capability produces or changes.

10. Human actions
    What a person must or may do.

11. Machine actions
    What an AI, tool, or module performs.

12. Human-AI collaboration mode
    Human only, AI only, shared, or supervised automation.

13. Dependencies
    Other capabilities, software, hardware, data, or permissions required.

14. Capability costs
    Compute, time, attention, setup, skill, and error-recovery cost.

15. Risks and limitations
    Failure modes, privacy risks, irreversibility, misuse boundaries, and
    unsuitable contexts.

16. Availability
    AVAILABLE, LIMITED, UNAVAILABLE, or UNKNOWN.

17. Maturity
    EXPERIMENTAL, WORKING, TESTED, STABLE, DEPRECATED, or UNKNOWN.

18. Proof status
    UNVERIFIED, DECLARED, DEMONSTRATED, TESTED, or INDEPENDENTLY_VERIFIED.

19. Learning difficulty
    BEGINNER, BASIC, INTERMEDIATE, ADVANCED, SPECIALIST, or UNKNOWN.

20. Interface needs
    Buttons, forms, canvas, timeline, file browser, code view, preview,
    controller, voice, dashboard, confirmation, or other requirements.

21. Related capabilities
    Prerequisites, dependencies, alternatives, combinations, and next steps.

22. Provenance
    Source type, location, hash, verification time, and confidence.

23. Freshness
    When the explanation and proof were last checked.

24. Unknowns and conflicts
    Explicitly preserved rather than smoothed over.

----------------------------------------------------------------------
3.2 THREE EXPLANATION DEPTHS
----------------------------------------------------------------------

QUICK VIEW

- One or two sentence explanation.
- One recognizable example.
- Main input and output.
- Main action.
- Primary risk or limitation.
- Suitable for menus, search results, and tooltips.

PRACTICAL VIEW

- Step-by-step usage.
- Required inputs.
- Expected output.
- Common mistakes.
- Limitations.
- Small exercise or guided example.
- Suitable for normal users and beginner interfaces.

DEEP VIEW

- Technical operation.
- Dependencies and contracts.
- Source evidence.
- Proof tests.
- Failure modes.
- Resource costs.
- Integration notes.
- Suitable for builders, teachers, maintainers, and AI collaborators.

The explanation layers must share the same source facts. Shorter layers may
compress detail but may not contradict or silently remove material warnings.

----------------------------------------------------------------------
3.3 LEARNING ATOMS AND COURSE GENERATION
----------------------------------------------------------------------

The Atlas should not only store fixed courses. It should store reusable learning
atoms that can be assembled into courses.

Course-generation inputs may include:

- target capability;
- learner type: human, AI, or mixed;
- current skill level;
- desired outcome;
- available tools;
- device;
- time budget;
- attention budget;
- compute budget;
- accessibility needs;
- required prerequisites;
- privacy or offline requirements.

Suggested learning path:

1. Orientation
2. Required concepts
3. Demonstration
4. Guided use
5. Independent exercise
6. Failure examples
7. Repair examples
8. Proof of successful use
9. Suggested next capabilities

A course must distinguish remembering an explanation from actually being able to
use the capability.

----------------------------------------------------------------------
3.4 KEY METRIC
----------------------------------------------------------------------

USABLE CAPABILITY COVERAGE

Definition:

The percentage of registered capabilities that have all of the following:

- a source-linked human explanation;
- an honest proof or maturity state;
- a usable interface route;
- a learning route;
- known risks and limitations;
- current provenance.

This prevents capability counts from being treated as equal to human usability.

4. MODULE B — AXM HUMAN INTERFACE INTELLIGENCE
======================================================================

WORKING NAME:
AXM Human Interface Intelligence

PURPOSE:
Pre-analyse capabilities, tasks, users, environments, and resource limits, then
determine which human interface pattern should expose a capability and which
beginner layer can achieve the intended goal with the lowest unnecessary cost.

PRIMARY QUESTIONS:

- Which human interface patterns work for this capability?
- Why do they work?
- Which patterns are unsuitable?
- Which beginner layer is safest and easiest?
- Which interface exposes enough power without unnecessary complexity?
- Which controls should be visible, hidden, restricted, or progressively
  disclosed?
- When should no interface be recommended?
- How should the recommendation change by device, skill, accessibility,
  privacy, offline need, risk, and reversibility?

The module must support:

- human-only workflows;
- AI-only operations that still require human oversight;
- shared human-AI workflows;
- supervised automation;
- beginner, normal, advanced, and specialist layers.

----------------------------------------------------------------------
4.1 INTERFACE PATTERN REGISTRY
----------------------------------------------------------------------

The module must maintain reusable interface patterns rather than hard-code one
interface for each capability.

Initial interface families:

- simple action button;
- guided form;
- wizard or step-by-step flow;
- searchable library;
- command palette;
- conversational interface;
- structured prompt builder;
- drag-and-drop workspace;
- node or graph editor;
- canvas;
- timeline;
- layer editor;
- property inspector;
- table or spreadsheet;
- dashboard;
- live preview with controls;
- before-and-after comparison;
- template selector;
- file browser;
- map or spatial interface;
- controller or game-style interface;
- voice interaction;
- automation recipe builder;
- code editor;
- hybrid visual-plus-code interface;
- approval and confirmation interface;
- monitoring and status interface.

Each pattern must record:

- suitable task types;
- unsuitable task types;
- minimum user skill;
- attention cost;
- interaction cost;
- setup cost;
- likely error rate;
- accessibility strengths;
- accessibility weaknesses;
- preview support;
- reversibility support;
- best input types;
- best output types;
- beginner suitability;
- advanced limitations;
- device suitability;
- offline suitability;
- privacy considerations;
- reasons for and against selection.

Important:

Conversational chat must not be assumed to be the correct interface for every
capability.

----------------------------------------------------------------------
4.2 BEGINNER-LAYER PRINCIPLES
----------------------------------------------------------------------

A beginner layer is not merely an expert interface with fewer visible buttons.

A valid beginner layer must:

- preserve the user's intended goal;
- remove unnecessary decisions;
- use safe defaults honestly;
- explain consequences before important actions;
- provide previews where possible;
- make mistakes recoverable where possible;
- clearly show what is simplified, restricted, or hidden;
- permit leaving beginner mode by user choice;
- never imply the simplified layer exposes the complete capability;
- minimize capability, compute, attention, and complexity cost;
- avoid manipulation, dependency-building, or hidden control;
- preserve an escalation path to advanced control.

Required distinctions:

- simplified control;
- restricted safe operation;
- guided advanced operation;
- full expert control.

----------------------------------------------------------------------
4.3 DETERMINISTIC SELECTION ENGINE
----------------------------------------------------------------------

Deterministic scoring must exist before relying on language-model judgement.

The engine should consider:

- capability input types;
- capability output types;
- task type;
- user goal;
- required precision;
- number of decisions;
- interaction complexity;
- interaction frequency;
- reversibility;
- risk;
- privacy sensitivity;
- need for preview;
- need for confirmation;
- skill level;
- device;
- accessibility needs;
- offline requirement;
- available tools;
- available compute;
- time budget;
- attention budget;
- complexity budget;
- setup cost;
- error-recovery cost.

The result must include reasons, not merely a rank.

Example:

Recommended:
Guided form with live preview.

Reasons:
- The capability accepts structured inputs.
- The user is a beginner.
- Changes are visual and reversible.
- Preview reduces error cost.
- Canvas editing would add unnecessary interaction complexity.
- Raw code would exceed the user's current skill requirement.

LLM assistance may later provide extra interpretation, but deterministic rules
must remain inspectable, testable, and usable offline.

5.1 KNOWLEDGE STATES
----------------------------------------------------------------------

Use explicit knowledge states:

KNOWN
INFERRED
UNKNOWN
CONFLICTED
NOT_APPLICABLE

Rules:

- KNOWN requires evidence.
- INFERRED requires a reason and source basis.
- UNKNOWN must remain unknown.
- CONFLICTED must preserve the competing claims and evidence.
- NOT_APPLICABLE must not be used as a shortcut for missing information.

10. LOCAL INTAKE PLAN FOR TOMORROW
======================================================================

When both build chats return packages:

STEP 1 — PRESERVE ORIGINALS

- Copy both packages unchanged into an intake staging folder.
- Record filenames, sizes, timestamps, and SHA-256 hashes.
- Do not merge immediately.

STEP 2 — LOCATE SHARED CONTRACTS

- Identify the shared-contract version in both packages.
- Compare schema files byte-for-byte where expected.
- Compare enumerations.
- Compare fixture identifiers.
- Compare field meanings.
- Record any drift.

STEP 3 — VALIDATE PACKAGES

- Run schema validation.
- Run unit tests.
- Run cross-module fixtures.
- Record pass, fail, skipped, and unavailable separately.
- Do not convert unavailable tests into passes.

STEP 4 — CONTRACT COMPATIBILITY

Check:

- contract_version;
- required fields;
- optional fields;
- enum compatibility;
- unknown handling;
- inferred-value evidence;
- migration support;
- source-reference format;
- recommendation status values.

STEP 5 — CROSS-MODULE ROUND TRIP

For every fixture:

1. Feed the original capability declaration into the Atlas.
2. Export the shared capability object.
3. Validate it.
4. Feed it into Interface Intelligence.
5. Produce an interface recommendation.
6. Validate it.
7. Compare it against expected fixture outcomes.
8. Confirm that source provenance survived the full route.

STEP 6 — HUMAN REVIEW

Review:

- whether explanations are understandable;
- whether risks remain visible;
- whether beginner layers remain honest;
- whether interface reasons make sense;
- whether advanced controls are preserved;
- whether cost claims are evidence-based.

STEP 7 — MERGE GATE

Only merge if:

- source provenance is preserved;
- shared schemas are compatible;
- critical tests pass;
- no silent capability expansion occurred;
- no destructive path lacks confirmation;
- no beginner layer falsely implies full capability;
- no fake proof or fake screenshot is included.

Otherwise place the package in TEST-HOLD-REVIEW with a repair list.
