   Stable evidence policy requires:
   - field
   - value
   - reasoning
   - source_basis
   - confidence
   - evidence_reference

   Implementation also emits:
   - rule
   - origin

   Conformance specifically requires for an INFERRED field:
   - reasoning

   Primary:
   source_reference

   It carries:
   - source_type

   - confidence

   Additional provenance may include:
   - source_pointer
   - source_line
   - adapter_id

33. Source location representation
   source_reference.source_location

   Record-level extraction position may additionally use:
   source_reference.source_pointer

   Strict policy expects deterministic pointer/line for multi-record sources,
   even though source_pointer is not a required core shared-schema property.

   Primary source bytes:
   source_reference.source_hash
   lowercase SHA-256 hex

   Other hashes:
   - normalized_source_sha256
   - normalized_source_canonical_sha256
   - normalized_source_semantic_sha256 in batch descriptors
   - enrichment_hash
   - enrichment_catalog_hash
   - enrichment_source_seal_hash
   - capability_card_canonical_sha256
   - plan_hash
   - batch_hash
   - batch_receipt_hash
   - manifest_hash
   - source_seal_hash

35. Freshness / staleness
   There is NO one global evidence-staleness enum on every evidence item.

   Implemented signals include:
   - source_reference.last_verified_at
   - module enrichment "freshness" copied from module registry
   - exact source hash verification
   - source seal verification
   - discovery-integrity verification
   - receipt_matches_source
   - registry snapshots/diffs
   - enrichment hash/source-seal hash changes

   A hash mismatch or changed source invalidates reuse.

36. Confidence values?
   YES.

37. What do confidence values mean?
   They may be:
   - source_reference confidence supplied/defaulted by adapter/source
   - deterministic format-detection confidence
   - deterministic inference-rule confidence
   - fixed rule values, e.g. generated human name confidence 0.65

   They are NOT automatically runtime success probabilities.
   Module 3 must preserve the origin/context of confidence.

38. Distinguishing proof levels

   DECLARATION EXISTS:
   - source declaration present
   - field may be knowledge state known within declared scope
   - public registry proof ceiling explicitly says declaration_is_runtime_proof=false

   STRUCTURAL VALIDATION PASSED:
   producer receipt validation may report:
   - shared_schema: PASS
   - stable_evidence_policy: PASS
   - stable_provenance_policy: PASS
   This means structure/evidence/provenance checks passed.
   It does NOT prove runtime behavior.

   SELF-TEST EXISTS:
   module context may include tests paths.
   discovery-verify checks declared path existence and declared promotion
   self-test hash where supplied.
   Module 1 does NOT execute upstream promotion self-tests.
   proof ceiling says selftest_is_human_approval=false.

   RUNTIME BEHAVIOR REPRODUCED:
   Requires separate reproducible execution/observation evidence tied to exact
   capability/revision/environment/procedure/result/artifact.
   Module 1 does not infer this from declaration, schema PASS, test-file
   existence, producer RUN, or enrichment VERIFIED.

   HUMAN VERIFICATION:
   Requires explicit reviewed human decision/evidence with appropriate authority.
   It is not implied by self-test existence or Module 1 packaging.

39. Can Module 1 promote declaration into runtime proof by itself?
   NO.

40. Explicit statement
   Module 1 MUST NOT promote a declaration, schema validation, provider join,
   producer run, batch PASS, or COMPLETE_VERIFIED status into runtime capability proof.

   Module 1 may CONSUME independently produced reproducible runtime evidence when
   provided with valid provenance, but the Atlas itself is not the capability
   executor that creates runtime proof merely by processing declarations.

42. UNKNOWN cause
   Insufficient evidence.
   Examples:
   - missing source field
   - unavailable evidence
   - unsupported assumption
   - partial/unresolved enrichment context
   - missing revision

   knowledge.unknowns must contain fields whose field_state is unknown.

43. CONFLICTED cause
   Two or more credible declarations/observations disagree.

   Examples:
   - declared vs observed field mismatch
   - capability/provider registry vs module contract mismatch
   - same capability ID/revision with materially different declarations

   Evidence must be preserved; no silent winner.

44. CONFIRMED cause
   NONE.
   There is no canonical CONFIRMED truth state.

   Do not generate or ingest CONFIRMED as Module 1 machine truth.
   If a UI wants a friendly label, it must map explicitly to a real machine state
   and must not replace the underlying token.

   inferred
   not_applicable
   plus known/unknown/conflicted above.

46. Can human rendering change truth state?
   NO.

47. Can missing field be silently invented?
   NO.

   Structural placeholder values may exist, but knowledge.field_states remains
   unknown and must be consulted.

   - both source claims
   - source locations
   - hashes

   - conflict state

   Resolution requires explicit reviewed resolution event.

49. Meaning of "Deterministic Humanization"
   Implemented deterministic operations include:
   - source normalization
   - deterministic ID-preserving adapters
   - deterministic title generation from machine_name when human_name is absent
   - deterministic registry-role classification
   - deterministic provider/module enrichment joins
   - deterministic humanization_seed
   - lexical provider-action candidate scoring
   - deterministic Quick / Practical / Deep view templates
   - deterministic learning/orientation templates
   - deterministic search/index construction

   Critical boundary:
   provider/module context and action candidates do not become capability facts.

50. Inputs determining human-readable card
   Primary:
   - normalized source capability record
   - source_reference/provenance
   - registry_context
   - enrichment_context when available
   - knowledge/evidence states
   - Module 1 implementation version/rules

   Derived views use the generated shared Capability Record.

51. Identical normalized input -> identical card output?
   NOT BYTE-FOR-BYTE GUARANTEED.

   The semantic humanization rules are deterministic for the same normalized
   semantics + Module 1 version.

   However full serialized artifacts contain volatile provenance/run metadata,
   especially:
   - source_reference.last_verified_at
   - producer run_id
   - completed_at timestamps

   Therefore two fresh builds of the same source can have different complete
   card canonical hashes because last_verified_at changes.

   Module 1 separately defines a portable semantic normalized hash that removes
   relocation/verification-time fields:
   portable_normalized_sha256 / normalized_source_semantic_sha256.

   Module 3 must distinguish semantic reproducibility from byte-identical run metadata.

52. Is an LLM required?
   NO.
   No LLM is required or implemented in the v0.10 humanization pipeline.

53. Optional LLM authority
   No optional LLM humanization path is implemented inside v0.10.

   If an external future process/Module uses an LLM to improve wording:
   - it has no technical authority by default
   - output must remain derived/inferred unless independently sourced/reviewed
   - it may not change capability_id, technical inputs/outputs, evidence state,
     or source facts without appropriate evidence/authority.

54. Summaries stored as facts or derived views?
   BOTH layers exist.

   Canonical shared card contains:
   - identity.human_name
   - purpose.*
   These carry evidence states and may be known/inferred/unknown.

   Derived presentation files:
   - quick_view.md
   - practical_view.md
   - deep_view.md

   Module-private humanization seed is contextual/derived evidence.

55. Can Module 3 regenerate views?
   YES, using the same shared Capability Record + compatible Module 1 view rules.

   For exact historical text, preserve:
   - Module 1 version
   - source/card record
   - relevant sidecar context

   Do not expect byte-identical timestamps/receipts from a fresh rebuild.
