## Reproduced defect

On a clean Windows worktree with `core.autocrlf=true`, the tracked observatory JavaScript and JSON files have Git LF blobs and CRLF working-tree bytes. The v0.1 adapter hashed raw working-tree bytes, so:

```text
node shared/heartbeat/observatory-deck-selftest.js
archive-intake-cartographer: review-digest-mismatch
actual: HELD
expected: READY
```

Recomputing the archive-intake digest from the seven Git-stored blobs produced the recorded review digest `ed57ea25bc0e161714d686a28211652a12e64c16cfc321a8a35d979f8729dd40`. The differing Windows digest came only from Git's checkout newline transform.

## Bounded correction

The adapter is now v0.2 and declares `sha256-canonical-text-lf-v1`:

- for the allow-listed `.js` and `.json` execution surface, a CR byte immediately followed by LF is omitted before each file SHA-256 is computed;
- lone CR bytes, byte-order marks, encoding bytes, paths, file inventory, and every non-newline content byte remain digest-significant;
- the aggregate module digest construction is otherwise unchanged;
- inspections, check-deck entries, and runner PASS output expose the digest contract;
- unknown modules, symlinks or junctions, missing selftests, non-TEST modules, and changed canonical execution bytes still fail closed.

This defines one reviewed Git-text identity across Windows and Unix without converting the execution files or weakening non-newline change detection.
