# Mirror Provider Declaration Research Exam Growth

Status: TEST

## Outcome

Mirror can now take a provider-declaration gap hand and originate the next
falsifiable research problem without a human manually writing a new exam for
each requirement.

The hard-coded Provider Declaration Research Exam Planner consumes every result
in the current declaration-hand batch. It creates an exam only for a verified
nonbuilt gap hand. Existing declarations, competing declarations, and absent
exact consumer demand create no exam.

The current immutable batch evaluates six hand results and originates one
research exam for `shared-physics`. It carries four architecture hypotheses:

1. reuse a typed shared-service declaration;
2. extend a typed engine or registry declaration;
3. introduce a new typed provider declaration; or
4. preserve unresolved because no architecture fits.

All four remain `UNTESTED`. No hypothesis is recommended or selected.

The exam specifies ten independent case families:

1. complete exact relation;
2. provider identity missing;
3. demanded selector coverage missing;
4. implementation target missing;
5. implementation content binding mismatch;
6. outside-root or symbolic target;
7. duplicate or competing provider;
8. permission declaration missing;
9. repaired declaration removes the next gap; and
10. existing declarations do not regress.

A future candidate may not author its own expected outcomes or held-out
fixtures. The exam planner selects no architecture, builds no executor or
fixture files, constructs no provider candidate, writes no declaration, runs no
experiment, changes no Workshop file, grants no permission, creates no training
receipt, and makes no readiness claim.

## Why this is progress toward autonomous growth

The earlier hand let Mirror say what relation was missing but stopped with “a
steward must resolve this.” The existing Frontier Cell could say that an
independent exam was required, but it did not create a content-addressed,
requirement-bound case specification. Organ Admission could propose an isolated
build, but it also did not author the exam.

The new organ bridges those existing capabilities:

```text
verified nonbuilt declaration hand
  -> typed architecture hypotheses, all UNTESTED
  -> typed held-out falsification, repair, regression and authority cases
  -> Frontier exam gate
  -> no answer, executor, fixture, provider or action
```

New requirement IDs and selectors flow through without adding them to Mirror's
code. A later exact provider removes the next exam while the previous immutable
batch remains evidence. This reduces manual curriculum work without giving a
generated candidate authority over its own grading.

## What worked and what did not

Worked:

- selector-bearing and bare consumer-gap fixtures both originated independent
  exams without requirement-specific rules;
- selector coverage became applicable only when exact demand carried a
  selector;
- existing provider declarations produced no exam;
- no-demand and ambiguous provider states held;
- the Frontier Cell independently classified every proposed exam as
  `FRONTIER_EXAM_REQUIRED`;
- the Reasoning Foundation selected the honest exam/no-exam path for every
  source result and rejected both premature provider construction and fake gap
  resolution;
- a later exact declaration removed only the next exam;
- old batches remained present and tampered private sessions were refused;
- automatic Workshop practice and Native Learning Shell reused the same batch
  while admitting zero exam requests, Frontier proposals, or discrimination
  sessions to training; and
- the authenticated loopback runtime returned the same exam and closed with
  zero memory writes.

Did not work or was intentionally not attempted:

- an initial evidence lookup assumed
  `C:\axm workshop\shared\pulse\service.contract.json`; that path does not
  exist. The failed lookup was not treated as evidence. An exact inventory then
  located the actual `visual-kernel` and `asset-hands` shared-service contracts,
  the foundation service plane, and the separate shared-engine declaration;
- current evidence does not establish which of the four architectures is
  correct;
- the research-exam request is not executable fixture code;
- no independent held-out fixture bytes have yet been authored;
- no provider identity, schema, path, content binding, permission declaration,
  or semantic fitness decision was made; and
- passing this planner's tests proves exam origination and boundaries, not that
  any provider architecture will pass the future exam.
