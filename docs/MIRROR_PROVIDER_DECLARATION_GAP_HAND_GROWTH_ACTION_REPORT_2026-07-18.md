## Outcome

Mirror now has one deliberately hard-coded but requirement-agnostic organ for a
narrow gap its existing organs could expose but could not represent:

- the Readiness Probe Affordance Planner can truthfully say that no exact
  provider declaration exists;
- exact consumer contracts can independently prove that a provider relation is
  demanded; but
- neither relation identifies the provider, declaration schema, contract path,
  implementation, availability, permissions, or semantic fitness.

The new Provider Declaration Gap Cell keeps those relations separate. The new
Provider Declaration Hand Planner may originate a reviewable, nonbuilt hand
only when one current affordance assessment has exactly zero provider
declarations and at least one exact `service:<requirementId>` consumer binding.
It evaluates every current affordance assessment and contains no Workshop
requirement or module ID list.

The current immutable batch evaluates six requirements. Five already have one
exact declaration and produce no gap. `shared-physics` alone produces a hand:

| relation | observed result |
| --- | --- |
| outer requirement | `shared-physics` |
| exact consumer binding | `service:shared-physics/axm-physics-2d` |
| exact provider declarations | 0 |
| provider selector carried by demand | `axm-physics-2d` |
| provider identity | `UNRESOLVED_NOT_INFERRED` |
| declaration schema | `UNRESOLVED_REQUIRES_STEWARD_SELECTION` |
| declaration target path | `null` |
| implementation path | `null` |
| implementation state | `NOT_BUILT` |

The selector is preserved because it may matter to a future declaration. It is
not promoted into provider evidence. The organ generated zero declaration
candidate files, wrote zero provider declarations, ran zero live probes,
changed zero Workshop files, granted zero permissions, created zero training
receipts, executed zero world actions, and made no `AVAILABLE` or `READY`
claim.

## Why a new organ was warranted

The existing readiness hand handles a different absence: a typed readiness
requirement has no live probe declaration. The affordance organ handles the
positive relation: one unique exact provider declaration may support a
structural-probe review packet. Extending either to choose a missing provider
would mix demand, provision, and readiness and would give consumer strings
hidden decision authority.

The added organ is therefore small and hard-coded around one reusable machine
relation, not one present-day service:

```text
current affordance assessment
  + zero exact provider declarations
  + one or more exact consumer service bindings
  -> nonbuilt provider-declaration gap hand
```

Existing declarations produce `DECLARATION_PRESENT_NO_GAP`. Competing
declarations produce `AMBIGUOUS_PROVIDER_DECLARATIONS_HOLD`. Zero exact
consumer bindings produces `NO_CONSUMER_BOUND_DECLARATION_GAP_HOLD`. None of
those states originates a provider decision.

## What worked and what did not

Worked:

- unseen fixture requirements and selectors entered without code changes;
- both selector-bearing and bare `service:<requirementId>` demand produced
  hands when providers were absent;
- an existing exact provider suppressed a hand;
- competing provider declarations held rather than multiplying providers;
- absent exact consumer demand held rather than inventing demand;
- a later exact provider removed the hand from the next content-addressed batch
  while the prior batch stayed immutable;
- tampering with preserved private evidence was refused;
- all assessments ran through the Reasoning Foundation against both a
  provider-inference candidate and a false-`AVAILABLE` candidate;
- automatic Workshop practice and the Native Learning Shell reused the same
  batch without admitting any hand or discrimination trace to training; and
- the authenticated loopback runtime returned the same bounded result and
  closed its session with zero memory writes.

Did not work or was intentionally not attempted:

- no existing evidence can decide whether `axm-physics-2d` is the provider ID,
  an adapter ID, a version selector, or another namespace;
- no evidence selects between a standalone shared-service contract, a service
  plane, an adapter registry, or a new exact declaration schema;
- the JavaScript adapter is implementation-shaped evidence but remains
  insufficient as provider-declaration authority;
- this organ does not build the next provider contract, because doing so would
  require attributed steward choices about schema, identity, target, source
  binding, permissions, and independent verification; and
- a PowerShell-wide `ConvertFrom-Json` check stopped on an existing
  `package-lock.json` parser quirk. It was not counted as success. Node's native
  JSON parser then verified the complete selected document set.

## Known limits and next gate

- This is structural relation evidence, not proof that a provider should be
  created or that `shared-physics` is semantically desirable.
- The current Technical Glasses observation remains `UNKNOWN` and was not
  mutated.
- The organ can preserve one or several demanded selectors but does not yet
  specify how conflicting selector semantics should be negotiated.
- A real provider-declaration build needs an attributed steward decision on
  identity, schema, target path, implementation binding, permission
  declarations, verification fixtures, and rollback. That should be a separate
  explicit reviewed candidate route, not an automatic extension of this hand.
- Learned weights cannot rewrite this cell, roots, permissions, evidence,
  review gates, or release gates.
- The result remains TEST and not CANON.
