# Molds, layers, and deterministic growth

Status: **WORKING / TEST**

## Why molds exist

A style cannot know how every present and future game is built. A mold is the
small semantic surface that both sides can agree on:

- a game declares which presentation slots it supports;
- a skin declares which semantic slots it can fill;
- the resolver filters unsupported properties;
- protected cues and game fallbacks remain authoritative;
- no gameplay or simulation field is accepted.

Sixteen built-in molds cover a universal core, worlds, structures, props,
vehicles, gear, loot, projectiles, characters, arcade arenas, RPGs, strategy,
party games, platformers, UI, effects, and the full current presentation
surface. Games can start with a small mold and adopt more slots later.

## Layer mixer

The layer composer can take world, structures/props, vehicles/equipment,
items/projectiles, character, interface, and effect presentation from different
skin packs. Materials, assets, and character blueprints are namespaced per
layer before composition. This prevents a material called `character.player`
in one source from replacing `world.base` in another.

Composition order is deterministic. Later layers can replace the same semantic
target, but they cannot write outside their declared scope.

## Mold maker

The recipe generator is not a hidden generative service. It is a deterministic
local style generator driven by:

- a visible seed;
- one of 16 molds;
- one of six moods;
- a visible complexity value;
- one of four performance profiles.

The same inputs produce the same intent and pack. In v0.6, generated bindings
are restricted to the selected mold's exact semantic slots and unused
materials/capabilities are omitted. A small mold no longer hides a 33-surface
pack.

Twenty portable starter kits are generated by `npm run molds:build`.

## Mold Foundry

The Mold Foundry is the part that creates new reusable surface molds.

- `forgeSkinMold(...)` builds a mold from an explicit list of known semantic
  surfaces.
- `growSkinMold(...)` starts from a built-in or user-supplied mold and adds or
  removes explicitly named surfaces or organs.
- `validateSkinMold(...)` rejects unknown surfaces, duplicate slots, hidden
  fields, and empty results.
- `createGameContractFromMold({ mold, ... })` turns an accepted custom mold
  into the same ordinary v1 game contract used by built-in molds.

Every forge/growth operation returns a receipt with its parent, additions,
removals, `DRAFT_REVIEW_REQUIRED`, and `automaticGameWrites: 0`. It does not
auto-promote, overwrite a built-in mold, inspect a game, or declare CANON.

## Integration boundary

Mold compatibility may inspect `adapterHints.semanticRole`, but it never changes
a binding automatically. A different game slot name requires an explicit
mapping through `remapPackBindings`. The mapping is recorded in provenance and
invalid targets remain rejectable by the normal validator.

## Performance profiles

- **Legacy / battery saver:** minimal glow and no pulse or shimmer.
- **Balanced:** practical default caps.
- **Showcase:** full allowed presentation range.
- **Reduced motion:** balanced materials with animation rates forced to zero.

Profiles only cap presentation materials. They cannot modify physics, input,
damage, scoring, economy, saves, or authoritative game state.
