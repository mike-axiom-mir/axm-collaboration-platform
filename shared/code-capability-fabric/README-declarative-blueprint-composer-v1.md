# Code Capability Fabric declarative blueprint composer v1

Status: `TEST`

This is the next bounded creation rung after the fixed slow-creation shell. It turns one exact, grounded-consent-scoped intent into one deterministic inert capability blueprint and a byte-bound receipt. The blueprint is data for later review and implementation; it is not executable code or authority.

## Capability added

The intent may declare up to 16 typed inputs, 16 typed outputs, 16 ordered transformation steps, 16 unproven quality claims, and explicit runtime-resource budgets. The composer validates that every step reads an available token, never overwrites one, and contributes to a declared output. It then derives:

- a provider-neutral interface and ordered composition graph;
- four-root and no-authority boundaries;
- an acceptance plan separating composer validation from future runtime proof;
- explicit `UNPROVEN` labels for desired semantic outcomes;
- exact intent, profile, blueprint, file-byte, consent-evaluation, and declaration lineage.

## Authority boundary

One invocation may write exactly `capability-blueprint.json` and `composition-receipt.json` under one new direct-child root selected by the trusted host. It reads no source or input artifact, uses no network, spawns no child process, emits no executable code, and executes no candidate. A failed attempt cleans only its newly owned root.

The interactive declaration remains a session gate, not cryptographic human identity, informed-understanding proof, replay prevention, trusted time, or live revocation. The intent declares `public-instruction`, but the composer does not inspect whether its text is actually public; the trusted host must keep private material out of this rung. The Fabric does not grant the external disposable write authority used by the host invocation.

## Honest interpretation

This proves deterministic specification composition, not semantic code generation. It can prepare a grounded handoff to a future provider, but no provider is invoked and no runtime behavior, quality, performance, installation, learning, promotion, merge, or CANON claim is made.

The fixed example composes a `bounded-code-change-proposal` blueprint from a change request, declared capability catalog, and known failures. Its acceptance plan makes future tests explicit before implementation.

## Next gaps

The receipt preserves authenticated human decisions, replay prevention, trusted time, live revocation, a blueprint-to-code provider, semantic candidate generation, runtime-quality verification in an explicitly authorized disposable sandbox, and a separate persistent-learning admission decision as open gaps.
